  • ☐ จัดหนึ่ง Source หรือชุด Source ที่เกี่ยวข้องใกล้กันต่อ Extraction Run
  • ☐ อ่านเฉพาะ Raw Source IDs ที่ Run ได้รับอนุญาต; ไม่ดึงทั้งคลังโดยอัตโนมัติ
  • ☐ สกัดทุกมิติใน coverage matrix รวมภาษา, รูปแบบ, transfer/handoff และข้อจำกัด ไม่เลือกเฉพาะข้อความที่สนับสนุนข้อสรุป
  • ☐ บันทึก Evidence แยกจาก interpretation โดยมี Source ID, ตำแหน่งตรง, excerpt/data, capture time/version, extractor/run และ coverage dimension
  • ☐ ทุกการตีความสร้างเป็น DERIVED และเชื่อมกับ Evidence; ห้ามเขียนทับ Raw
  • ☐ เขียน Evidence ไป store จริงและอ่านกลับ; เก็บ ID/link ที่ระบบคืนให้
  • ☐ หากเข้าถึงหรือเขียนไม่ได้ ให้ BLOCKED/NOT_WRITTEN พร้อม Source ID/path และ error ที่พบ; ห้ามบอกว่า Source ไม่มี

Output: source-linked evidence records + completed coverage rows
Exit Gate: Gate อิสระยืนยัน completeness ก่อน freeze ชุดข้อมูล

WP-04 — Reconstruct fixed lifecycle and project topics

  • ☐ ใช้ 6+6 เป็น fixed user-reported baseline; ค้น/อ่าน skill หรือ Source ที่กำหนดชื่อจริงก่อนเขียนรายละเอียด
  • ☐ ดึงชื่อ, ลำดับ, inputs, outputs, dependencies, branches, pause/resume, backward/return conditions ของ 6 forward และ 6 backward จาก Source จริง; ห้ามประดิษฐ์ชื่อหรือ transitions
  • ☐ สกัดหัวข้อหลักทั้งหมดจาก Source conversation; นับจากหลักฐาน ไม่บังคับจำนวนประมาณ 20 หาก Source ไม่ยืนยัน
  • ☐ ทำ map topic/lifecycle step → evidence IDs → inputs/outputs → dependency → responsible module
  • ☐ วาดเป็น directed graph; edge ต้องระบุเงื่อนไข forward, backward, branch, pause, resume และ rework
  • ☐ แยก lifecycle 6+6 ออกจาก package phases 0–3 และ WP-00–WP-13

Output: source-grounded lifecycle map + topic/evidence map
Exit Gate: ทุกชื่อ/edge/topic เชื่อม Source หรือ decision ที่อนุมัติ; ไม่มีส่วนที่ AI เติมเอง

WP-05 — Cross-platform data contracts

  • ☐ กำหนด record schemas สำหรับ Source metadata, normalized data, export package, import result, transformation และ error report
  • ☐ สำหรับทุกคู่ platform ให้ map field ต้นทาง→ปลายทาง, format, encoding/language, attachments, links, metadata, unsupported fields, loss และ round-trip behavior
  • ☐ กำหนด required/optional fields, versioning, validation และ compatibility policy จากหลักฐาน/การตัดสินใจที่อนุมัติ
  • ☐ เก็บค่าต้นฉบับ; transformation สร้าง derived version ใหม่ ไม่แก้ Raw/Frozen
  • ☐ ใช้ตัวอย่าง input/output จริงที่มาจาก Evidence; ห้ามสร้าง threshold ที่ไม่มีแหล่ง

Output: canonical schemas + platform mapping tables
Exit Gate: ทุก transfer route มีตัวอย่างจริงและ acceptance criteria ที่ตรวจซ้ำได้

WP-06 — Build Adapters/Skills incrementally

  • ☐ สร้าง Adapter ทีละตัวจาก workflow ที่อนุมัติ; ไม่ติดตั้ง/รวม catalog ทั้งหมดอัตโนมัติ
  • ☐ Manifest ระบุ purpose, trigger, inputs, allowed source scope, ordered steps, branches/return conditions, tool IDs, artifact IDs, output schema/path และ Gate criteria
  • ☐ ID หลัก/เวอร์ชัน/Step IDs มาจาก Registry; ห้าม AI ตั้ง IDs จริง
  • ☐ แยก Adapter ออกจาก master lifecycle จนกว่าจะผ่าน validation ของตัวเอง
  • ☐ ติดตั้ง/เผยแพร่ version ใหม่โดยไม่เขียนทับ workflow หรือ Adapter เก่า

Output: versioned Adapter manifests + step definitions
Exit Gate: Adapter ถูกเลือกและทำงานได้ในขอบเขตโดยไม่โหลดโมดูลที่ไม่เกี่ยว

WP-07 — Bind tools and artifacts

  • ☐ บันทึก Tool ID/name/provider/callable capability/parameters/permissions/expected response/failure modes/safe retry rule จาก tool จริง
  • ☐ ตรวจ schema ของ Tool ที่ callable ในห้องนั้น; ห้ามสรุปว่าเรียกได้จากชื่อหรือคำอธิบาย
  • ☐ ทดสอบ Tool ขั้นต่ำแบบ non-destructive ก่อนใช้จริง; จด response และ error
  • ☐ Artifact record ระบุ ID/type/schema/producer Adapter-step/source inputs/storage path/version/consumers
  • ☐ ทำ Adapter-to-Tool/Artifact map และตรวจทุก dependency ว่ามีจริงและได้รับอนุญาต

Output: Tool Registry + Artifact Registry + binding map
Exit Gate: ทุก dependency resolve ได้และผ่าน minimal invocation test

WP-08 — Independent Gate

  • ☐ กำหนด Gate แยกจาก execution; Gate อ่านหลักฐาน/ผล แต่ไม่ทำงานแทน Adapter
  • ☐ Gate โหลด Adapter version, Run manifest, ACTIVE_INPUT_IDS และ criteria เฉพาะงานที่ตรวจ
  • ☐ ตรวจ lineage/source, route/direction, tool invocation evidence, output schema, completeness และ task criteria
  • ☐ กำหนดผล PASS, REWORK, BLOCKED, NOT_APPLICABLE พร้อมเหตุผลและหลักฐาน
  • ☐ เมื่อ REWORK ระบุ criterion ที่ตก, Evidence/Artifact ID, Adapter Step ID และ return route; การแก้สร้าง version ใหม่แล้วตรวจซ้ำ
  • ☐ ให้ reviewer ทำซ้ำเหตุผลการผ่าน/ไม่ผ่านได้; worker self-report ไม่ใช่หลักฐาน PASS

Output: Gate contract + decision record schema
Exit Gate: Gate decision ตรวจซ้ำได้และไม่ self-certify

WP-09 — Checkpoint and recovery

  • ☐ Checkpoint fields: checkpoint ID, project/phase/task/run IDs, room/agent, creator/time, Adapter version, active inputs, last completed step, output IDs, Gate status, next permitted step, prior checkpoint
  • ☐ ทุกห้องเริ่มโดยโหลด manifest/checkpoint ล่าสุดและตรวจ version/IDs ก่อนทำงาน
  • ☐ หลังจบแต่ละ step เขียน checkpoint ใหม่และอ่านกลับ; ห้ามรายงาน progress saved หากไม่มี record ID/link
  • ☐ หาก version เปลี่ยนหลังอ่าน ให้หยุดก่อนเขียนและบันทึก conflict; ห้าม overwrite
  • ☐ ทดสอบ resume ในห้องใหม่โดยใช้ Packet/Checkpoint เดิม โดยไม่ต้องพึ่งแชทเก่า

Output: checkpoint record + restart procedure
Exit Gate: ห้องใหม่กลับมาทำต่อจาก next permitted step ได้ตรงจุด

WP-10 — Freeze, append-only, conflicts and TEMP

  • ☐ กำหนด FROZEN = immutable/readable; ไม่ใช่ Active Input โดยอัตโนมัติ
  • ☐ Append-only ใช้กับ Evidence/audit; สร้าง record/version ใหม่ได้; record เก่าไม่ถูกแก้/ลบ
  • ☐ เปรียบเทียบ conflict เฉพาะ scope/field ที่เทียบกันได้ ด้วย authority/version/date rule ที่กำหนดไว้; บันทึก delta
  • ☐ Comparison สร้าง Artifact ใหม่เชื่อม source IDs ทั้งคู่; ห้าม merge old/new เข้า record เดียวเอง
  • ☐ TEMP ระบุ purpose/owner/source/destination/expiry/closure action; ไม่กลายเป็น permanent fact โดยอัตโนมัติ
  • ☐ ทดสอบว่ากฎไม่กลายเป็น “ห้ามสร้างข้อมูลใหม่” แบบครอบจักรวาล

Output: record lifecycle/conflict/temporary-data policy
Exit Gate: freeze/append-only/expiry ใช้ตาม scope และตรวจ audit ได้

WP-11 — Fully populated room packets

  • ☐ Packet ต้องมีข้อมูลจริงก่อนส่ง; unresolved placeholders = not dispatchable
  • ☐ ระบุ Project/Room/Task/Phase/Run IDs, Source/Evidence/Artifact IDs และ locations, Adapter/version, permitted Tool IDs, objective, scope/exclusions, ordered steps/branches, output schema/path, write/read-back, Gate criteria, next route
  • ☐ แนบเฉพาะ evidence/data payload ที่ห้องต้องใช้จริง พร้อม source locations; ห้ามส่งแค่ลิงก์หรือโครงเปล่าเมื่อห้องไม่มีสิทธิ์เปิดต้นทาง
  • ☐ First command ทำ bounded unit ได้โดยไม่ถามซ้ำเมื่อ input/tool/permission ครบ
  • ☐ เมื่อเข้าถึงไม่ได้ ให้หยุด Run เป็น BLOCKED, ระบุ ID/path/tool error และ recovery item; ห้ามเดา/แทน Source/เริ่มโครงการใหม่
  • ☐ แยก response: STORED_EVIDENCE, DERIVED_ANALYSIS, OUTPUT_ARTIFACT, CHECKPOINT, CHAT_STATUS

Output: ready-to-paste prompt packet per room, fully populated
Exit Gate: แต่ละ Packet self-contained, scope ถูกต้อง, อ้าง Registry เดียวกัน

WP-12 — End-to-end pilot; repair observed failures only

  • ☐ เลือกหนึ่ง Source, Extraction Adapter, Tool, Output Artifact, Gate และ downstream consumer
  • ☐ ทดสอบ raw access boundary → coverage → extraction → write/read-back → freeze → retrieve by ID in a new room → downstream output → independent Gate → rework if needed → resume from checkpoint
  • ☐ ทดสอบ context loss/stale chat, missing source ID, tool failure, partial extraction, old/new conflict, Adapter version change และ TEMP expiry
  • ☐ ทุก failure เป็น versioned issue มี reproduction steps, expected/actual, evidence, severity/impact และ owner; ห้ามแก้เกินปัญหาที่พบโดยไม่มีเหตุผล
  • ☐ เก็บ prior runs; fix เฉพาะ contract/Adapter version ที่เกี่ยวข้องและ rerun Gate

Output: pilot report + issue log + approved changes
Exit Gate: ผ่านโดยไม่มี cross-room contamination, silent overwrite, false saved claim หรือ untraceable handoff

WP-13 — Human approval, publish, maintain and close

  • ☐ Human review master map, source counts, schemas, Adapter/Tool bindings, Gate policy และ pilot evidence
  • ☐ หาก Git repository จริงเข้าถึงได้: publish ผ่าน protected main/PR ตาม policy ที่ตรวจจาก repo จริง; ห้ามสมมติ branch policy จากข้อความ AI
  • ☐ Version เอกสาร/schema/Adapter/packet; เก็บ change log และ compatibility notes
  • ☐ ปิดงานด้วยการ archive permanent artifacts, จัดการ TEMP ตาม policy, คง audit history และบันทึก final status
  • ☐ ทดสอบ Fresh Room: โหลด manifest, input IDs, ทำงาน, write/read-back, Gate และส่งต่อได้โดยไม่ใช้ history ของห้องก่อน
  • ☐ บันทึก human approval และผู้อนุมัติ; จึงประกาศ operational readiness

Output: approved/versioned/restartable project package
Exit Gate: Fresh Room ทำ end-to-end route ได้; human approval มีหลักฐาน; ไม่มี open blocker ที่ซ่อนอยู่

3. แกนแพ็กเกจ 0–3 (แยกจาก Lifecycle และ WPs)

  • ☐ Package Phase 0 — Registry/Source setup: project identity, source/store locations, IDs, permissions, counts scope
  • ☐ Package Phase 1 — Extraction: authorized room extracts raw sources and fills coverage before handoff
  • ☐ Package Phase 2 — Synthesis: downstream uses verified Evidence/Artifact only; reconstructs workflow/topics without reopening Raw
  • ☐ Package Phase 3 — Task/Room decomposition: creates Adapter/Tool/Artifact bindings and populated room packets
  • ☐ Gap return: downstream gap names missing dimension/source ID and routes back to Phase 1; no raw access from unauthorized phase

Mapping to WP-00…WP-13 ต้องทำเป็นตารางแยกและอนุมัติ; ห้ามถือว่า Phase 0–3 เท่ากับ WP-00…WP-13 หรือ Lifecycle 6+6

4. Room Packet release gate

ก่อนส่งให้ห้องใด ให้ตรวจทุกข้อ:

  • ☐ IDs มาจาก Registry; ไม่มี ID ที่ AI ตั้งเอง
  • ☐ Source/Evidence/Artifact IDs และตำแหน่งจริงอ่านได้
  • ☐ Payload มีเนื้อหาหลักฐานที่ห้องต้องใช้ ไม่พึ่งการเปิดแชทเดิม
  • ☐ Active inputs และ exclusions ชัด; ไม่มี auto-merge
  • ☐ Adapter/Tool/version/permission ผ่านการตรวจในห้องที่จะใช้
  • ☐ ขั้นตอน, branch, backward/return conditions, output schema/path และ Gate ครบ
  • ☐ Write/read-back และเส้นทาง BLOCKED/NOT_WRITTEN ระบุครบ
  • ☐ Next permitted step ชัดเจน; ไม่มีคำสั่งให้ Agent เดา/ถามข้อมูลที่มีใน Packet

5. Project Definition of Done

  • ☐ Source inventory exhaustively captured with dated snapshot; page/project/topic counts แยกกันและตรวจซ้ำได้
  • ☐ Evidence coverage ทุก required dimension ครบหรือมี NOT_APPLICABLE พร้อมเหตุผล
  • ☐ Lifecycle 6+6 ถูกถอดจาก skill/Source จริง; ทุก step/edge/topic เชื่อม Evidence/decision
  • ☐ IDs, schemas, stores, permissions และ versions ถูกกำหนด/อ่านกลับผ่าน Registry จริง
  • ☐ Adapter และ Tool ทุกตัวมี invocation evidence, failure handling และ independent Gate
  • ☐ Room packets ทุกชุดมี payload จริง, scope ถูกต้อง, พร้อมใช้ในห้องใหม่โดยไม่อาศัย old chat
  • ☐ Pilot ผ่านกรณีปกติและ failure tests; Run, Evidence, Artifact, Gate, Checkpoint ตรวจย้อนกลับได้
  • ☐ Frozen data ไม่เปลี่ยน, TEMP ปิดตามกฎ, audit/version history อยู่ครบ
  • ☐ Fresh Room resume test ผ่าน; Human approval บันทึกแล้ว
  • ☐ ทุก control ที่ยังไม่ทดสอบหรือ risk คงเหลือถูกระบุ; ห้ามประกาศ “ปิดครบ” จาก checklist อย่างเดียว
